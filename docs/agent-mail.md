# Agent mail

A fleet of agents that work asynchronously and talk to each other by
email.

Everything else in this repo runs *one* agent: you write a handoff,
`fork-sandbox run` puts a session in a sandbox, and a branch comes back.
Agent mail is the layer above that. Agents here are email-equipped
virtual workers with standing instructions and a mailbox. You mail one of
them; it wakes up in a sandbox, reads the thread, does something, and
replies. Its reply is mail too, so it can wake somebody else. The
conversation is the program.

Three scripts and a renderer, each doing one job and knowing nothing
about the next:

| Script | Job | Knows about |
|---|---|---|
| `fork-sandbox mail` | the store: write and read messages | files under the mail root |
| `fork-sandbox fleet` | the registry: who the agents are | personas and `fleet.yaml` |
| `fork-sandbox postmaster` | the router: wake agents, harvest replies | all of the above, plus `fork-sandbox run` |
| `fork-sandbox-mail-render.py` | the view: a thread as HTML or as text | the store's file format |

The store has never heard of an agent. The registry has never heard of a
message. Only the postmaster knows both, and it is the only piece that
spawns anything.

## The mental model

**An agent is a (persona, mailbox) pair.** The persona is a markdown file
of standing instructions; the mailbox is an `@name` address. Nothing else
constitutes an agent — there is no process, no daemon, nothing running
between wakes.

**Addressing is the whole mechanism.** `To:` wakes an agent. `Cc:` does
not: a Cc'd agent receives the message (it shows up in its `inbox`, and
the full thread arrives in its prompt whenever it *is* next woken) but
costs nothing until someone addresses it directly. That asymmetry is what
makes a "maintainer who mostly watches" seat free.

**The thread is the memory.** Every wake carries the entire thread in its
prompt. Session resume exists (below) and saves real money, but it is an
optimization: an agent whose session is lost, or whose harness cannot
resume at all, still has everything it needs.

**Privacy is addressing, not access control.** There are no ACLs. A
private conversation is just a thread whose recipients are its
participants. An agent's world is the thread it was woken for — the
sandbox has no mail tooling and no store access, so what is embedded in
its handoff is all it can see. On the host, the store is a directory of
plain files and you can read all of it.

**Real email is the model.** Whenever a design question has an email
answer, this takes the email answer: RFC 5322-shaped headers, reply-all
by default, `Re:` subjects, `> ` quoting that nests to `> > `, mailing
lists that stay unexpanded in the archive.

## The store

`fork-sandbox mail` is a shared maildir-style message store. It writes
and reads; it never routes, never spawns, and has no idea whether an
address belongs to anything real.

```bash
fork-sandbox mail send --from @operator --to @reviewer,@scribe \
    --subject "patch 3 of the series" --body ./note.md
fork-sandbox mail reply --from @reviewer --reply-to <message-id> --body -
fork-sandbox mail show  <message-id>
fork-sandbox mail tree  <thread-id>
fork-sandbox mail list
fork-sandbox mail inbox reviewer [--all]
fork-sandbox mail seen  reviewer <message-id>...
```

### Layout

Under `$FORK_SANDBOX_MAIL_ROOT` (default
`/var/tmp/claude-scratch/agent-mail`):

```
<root>/threads/<thread-id>/<NNN>-<uuid>.msg     NNN = 3-digit arrival seq
<root>/threads/<thread-id>/attachments/<basename>
<root>/agents/<name>/seen                       append-only message-id list
<root>/.postmaster/                             router state (see below)
```

A thread id is the Message-ID of the message that started it, so a thread
root's `Message-ID` and `Thread-ID` are equal. `NNN` counts arrival order
within the thread and starts at `001`.

### Message format

RFC 5322-shaped: a header block, a blank line, the body verbatim.

```
Message-ID: <uuid>              generated by the store, never caller-supplied
Thread-ID: <root uuid>
Date: <RFC 2822, UTC>
From: @<name>
To: @<name>[, @<name>...]
Cc: @<name>[, @<name>...]       omitted entirely when empty
Subject: <text>
In-Reply-To: <parent uuid>      replies only
References: <uuid> <uuid>...    replies only, root-to-parent order
X-Hops: <int>                   default 8 on a new thread
X-Attachment: attachments/<basename>    one line per attachment
```

Ids are bare uuids: no angle brackets, no `@domain`. `Message-ID` and
`Thread-ID` are literal uuid values.

A `reply` with no `--to` is reply-all: the parent's `From` + `To` + `Cc`,
deduped, minus the sender. Its subject defaults to `Re: ` + the parent's.
Its `X-Hops` is **copied verbatim** from the parent — decrementing is the
router's job, not the store's, and `--hops` is the override the router
(or an operator) uses to do it.

### Addresses

Every address matches `^@[a-z0-9][a-z0-9-]*$` — lowercase alphanumeric
and hyphens, no leading hyphen. Anything else is refused. The store does
not consult the registry: an address here is a string, not a claim that
anyone will answer.

### Attachments, and the things that are refused

Attachments are copied into the thread's `attachments/` directory, capped
at 4 MiB each. The directory is flat and keyed on basename alone, so:

- a basename already staged with **different** content is refused —
  overwriting it would leave an earlier message's `X-Attachment` pointing
  at the wrong bytes;
- identical content under the same basename is accepted silently (two
  messages may legitimately share one file);
- two `--attach` arguments in one command that collide on basename and
  differ in content are refused for the same reason;
- a basename containing a newline is refused, because the staged list is
  `/`-joined and split with `read -ra`, which would silently truncate it.

Header values containing raw newlines are refused everywhere, including a
caller-supplied `--subject`. Everything up to the first blank line parses
as headers, so a newline in a value forges or truncates header lines.

### Concurrent posts

Two messages landing in one thread at once race for the same `NNN`. The
store resolves this with an `mkdir` lock rather than check-then-write: a
poster reserves `<NNN>.seq`, a directory name carrying no uuid, so two
posters guessing the same number contend for the *identical* path and
`mkdir` fails atomically for the loser. The loser bumps and retries. A
failure that is not "slot taken" — permission denied, ENOSPC, a read-only
thread directory — aborts with a diagnostic instead of spinning, since
retrying fixes none of those.

Reservation directories are never removed. Removing one would free the
number for reuse while a message still occupies it, which is the
duplicate-`NNN` bug the scheme exists to prevent.

### What `inbox` is for

`inbox <name>` is the one privacy-shaped verb: it surfaces only messages
naming `@<name>` in `To` or `Cc`, unseen by default, all of them with
`--all`. `show`, `tree`, `list` and a plain `grep` of the store see
everything — they are host-side operator tools. An agent that only calls
`inbox` for its own name sees only its own mail; anything with
filesystem access to the store sees all of it.

## The fleet registry

`fork-sandbox fleet` answers "who are the agents, and what seat does each
one run on". It has two sources of truth, machine config winning over
content.

**Persona files**, `<personas-dir>/<name>.md`
(`$FORK_SANDBOX_PERSONAS_DIR`, default
`~/.config/fork-sandbox/personas`): a markdown body — the agent's
standing instructions, opaque to the registry — with optional YAML
frontmatter carrying `description`, `harness`, `model`, `network`
(`pinned` or `sealed`) and `thinking`.

```markdown
---
description: reads patches like a maintainer, slow to approve
harness: claude
model: opus
---

You are a kernel maintainer reviewing a patch series. Be specific...
```

**The fleet file** (`$FORK_SANDBOX_FLEET_FILE`, default
`~/.config/fork-sandbox/fleet.yaml`): a YAML mapping of `agents` and
`lists`.

```yaml
agents:
  reviewer:
    persona: reviewer.md      # a filename under personas-dir, never a path
    model: opus
  scribe:
    harness: pi
    network: sealed
  watcher: {}                 # persona watcher.md, no overrides
lists:
  crew:
    members: [reviewer, scribe, watcher]
```

Precedence per field is **fleet.yaml entry, then persona frontmatter,
then empty**. The registry reports what is configured and applies no
defaults of its own — an agent may resolve with every field empty, and
that is valid output, not an error. Whoever consults the registry owns
the defaulting policy.

A bare `<name>.md` in the personas directory makes `name` an agent on its
own, with no fleet-file entry needed. A `persona:` override names a file
directly under the personas directory, not a path.

`network: sealed` is legal only against `harness: pi`, and is checked
both within one document and against the merged result — either document
can be individually valid and still combine into an illegal seat. The
one-word spelling `pi-local` that presets accept is deliberately refused
here; the registry takes the two-axis form only.

### Verbs

```bash
fork-sandbox fleet check              # validate everything, report every error
fork-sandbox fleet resolve <name>     # six lines: harness, model, thinking,
                                      # network, persona-path, description
fork-sandbox fleet expand @crew,@ci   # a list becomes its members, deduped
fork-sandbox fleet roster             # human-readable summary
fork-sandbox fleet teardown <agent> [--thread <id>]
fork-sandbox fleet teardown --all     # destroy persistent (thread, agent)
                                      # seat state: the workspace clone, the
                                      # session record, the session state dir
```

`check` accumulates every error across the fleet file and every persona
it declares — addressed by path, like `agents.reviewer.modle` — rather
than stopping at the first. `resolve` always prints exactly six lines;
an unconfigured field is an empty line, never a missing one.

`teardown` is how an operator reclaims a seat's persistent state (the
`workspaces/`, `sessions/` and `state/` rows in the table above) once a
thread is done with it — nothing else ever removes them. `<agent>` alone
tears down every thread that agent has a seat on; `--thread` narrows to
one seat; `--all` tears down every seat found. It refuses, by name, any
seat with a live, not-yet-harvested run rather than pull a workspace out
from under a running sandbox.

A missing fleet file is not an error by itself: `resolve` and `expand` of
a bare agent still work from persona files alone, which makes a personas
directory with no fleet file a valid fleet of unlisted agents. `check`
and `roster` report on the fleet file as a whole and require it.

### Lists expand at routing time, never in the archive

`expand` turns `@crew` into its members *at the moment it is called*. A
message already in the store keeps whatever address it was sent to, list
or agent, unexpanded — exactly as a real mailing-list archive keeps
`To: list@example.com` rather than rewriting it to every subscriber.
Change a list's membership and past mail is unaffected; future routing
uses the new membership.

## The postmaster

`fork-sandbox postmaster` is the host-side router: it watches the store,
wakes addressed agents by spawning `fork-sandbox run`, harvests their
replies back into the store, and enforces the stop rules.

```bash
fork-sandbox postmaster deliver --project ~/src/proj [--once]
fork-sandbox postmaster status
fork-sandbox postmaster flag   <thread-id> [reason]
fork-sandbox postmaster unflag <thread-id>
```

`deliver` loops — scan, route, harvest, sleep
`$FORK_SANDBOX_POSTMASTER_INTERVAL` seconds (default 15) — until
SIGTERM/SIGINT. `--once` does a single pass and exits. `status` prints
one screen: unrouted count, every live run, every thread flagged
needs-operator with its reason, each thread's spawn count. `flag` and
`unflag` set that flag by hand — to silence a thread you intend to leave
alone, or to re-arm one after fixing whatever tripped it.

### Routing rules

Applied in order to each unrouted message M in thread T. A message is
routed exactly once, and the decision is made before any wake is spawned
for it.

0. **Expand M's `To`**, one address at a time, so an unknown address
   elsewhere in the same `To` cannot fail the whole batch. Every expanded
   name that resolves as a fleet agent is a wake candidate. A name that
   does not resolve — unknown, or external like the operator's own
   address — is skipped silently; external senders receive mail only in
   the archive. M's own `From` is never a candidate, even when it reaches
   the list only through a list address: a sender never wakes on its own
   message.
1. **Operator reset.** If M's `From` does *not* resolve as a fleet agent,
   M is operator or external mail: clear T's needs-operator flag and
   reset T's spawn count to 0 *before* applying rules 2–3 to M. An
   operator re-arms a stalled thread simply by mailing into it. Raising
   hops is separate, and needs `mail send --hops` on a fresh thread — an
   operator's `mail reply` copies the parent's `X-Hops` verbatim like any
   other reply.
2. **Hops gate.** `X-Hops == 0` means no wakes from M. Flag T
   needs-operator, reason `hops exhausted at <message-id>`.
3. **Thread budget.** Spawns so far ≥ budget (default 12,
   `$FORK_SANDBOX_THREAD_BUDGET`) means no wake. Flag T, reason
   `thread budget <n> exhausted`. This is checked once per message, not
   once per candidate: a message addressing four agents with one slot
   left still spawns all four. v1 does not ration within a single
   message.
4. **One wake per (agent, message).** An agent named twice — directly and
   via a list — wakes once. An agent already running a wake for T does
   not get a second spawn; the new message id is recorded on that run as
   a pending message, and after harvesting that run's reply, rules 2–3
   are re-checked and a follow-up wake is spawned for the newest pending
   message if they still pass.

Together with "an agent may originate a reply only when it is in `To`",
those rules are the stop rules. Hops bound the depth of a conversation,
the budget bounds its total spend, and the operator can reset both.

### The wake

A wake is one `fork-sandbox run` with **no review loop and no maintainer
loop**. That is deliberate: on a fleet, the fleet is the review — scrutiny
comes from other agents reading the reply on the thread, not from a
second model reading the diff.

The seat comes from `fleet resolve`. Unset harness and network default to
`claude` and `pinned`. An unset model defaults to `sonnet` **only on the
claude harness** — `sonnet` is a claude alias, so defaulting it for pi or
codex would hand a bogus model to a harness that does not know the name,
or defeat `fork-sandbox.sh`'s own model-less-pi guard and a sealed seat's
model discovery. Those harnesses get no `--model` at all, and
`fork-sandbox.sh`'s ordinary resolution applies.

Branches are named `sbx-mail-<first8-of-thread-id>-<agent>-<seq>`, where
`seq` comes from a thread-lifetime counter that is **never** reset —
unlike the budget counter, which rule 1 does reset — so a branch name can
never repeat within a thread. A wake that commits nothing is normal; an
analysis reply has no code, and `fork-sandbox.sh` deletes empty branches
itself.

The generated handoff embeds everything the sandbox needs and nothing it
could reach on its own: "You are @\<agent\>", the persona's markdown body
with frontmatter stripped, the thread, the triggering message id called
out, the reply-file format, the transparency norm (private side-channels
are fine, but say on-thread if one shaped your reply), and — importantly
— *no reply is a valid outcome, end your turn*. An agent is one voice on
a team, not obliged to speak every time it is woken.

### Replies

A wake replies by writing one file per outgoing message into its run's
artifact outbox, named `mail-*.md`:

```
To: @a, @b              # optional; default is reply-all to the trigger
Cc: @c                  # optional
Subject: ...            # optional; default "Re: " + the trigger's subject
Reply-To-Id: <id>       # optional; default the triggering message id.
                        # The literal string "new" starts a NEW thread
                        # instead, and then To and Subject are required —
                        # there is no parent to reply-all from.

body...
```

Once a run reaches a terminal state — `summary.json` in its run dir
(`fork-sandbox.sh`'s last artifact, written after cleanup and the branch
fetch-back), or a dead pid with no `summary.json` ever landing — the
harvester posts each file through `fork-sandbox mail`, as
`--from @<agent>`, passing `--hops` explicitly as the trigger's
`X-Hops` minus one. That is the only place the decrement happens, on both
the ordinary-reply and the new-thread path.

A non-zero exit, and a wake that died without writing `summary.json`, are
harvested exactly like success — their outbox, if any, is still posted —
but they also flag the thread: an empty outbox from a crashed wake is not
the documented "no reply is a valid outcome", and needs an operator's
eyes.

A malformed reply file — bad address, unparseable stanza, or a `mail`
call that itself fails — is skipped and flags the thread with the
filename and the reason. It never costs the run's other, well-formed
replies. The run is then marked harvested exactly once.

Posted replies are new unrouted messages. The next scan routes them. That
loop is the whole conversation.

### Router state

Under `$FORK_SANDBOX_MAIL_ROOT/.postmaster/`, dot-prefixed so the store's
own thread scans never see it:

| Path | What it is |
|---|---|
| `lock` | a `flock`'d file; the pid inside is for messages only — the mutual exclusion is the kernel's advisory lock, so a killed postmaster cannot leave a stale hold |
| `routed/<message-id>` | routing already decided for this message |
| `runs/<run-id>.env` | one spawned wake: agent, thread, trigger, run dir, branch, resumed session id, pending messages |
| `harvested/<run-id>` | this run's outbox is collected |
| `needs-operator/<thread-id>` | flag file; its content is the reason |
| `spawns/<thread-id>` | one line per spawn, reset by rule 1 — line count is the **budget** count |
| `seq/<thread-id>` | one line per spawn, never reset — feeds the branch name |
| `handoffs/<run-id>.md` | the generated handoff a wake was given |
| `state/<thread-id>/<agent>/` | the claude transcript store for that pair |
| `sessions/<thread-id>/<agent>` | the session id that pair's last wake ended on |
| `workspaces/<thread-id>/<agent>/` | the persistent clone for that (thread, agent) seat, bound into every wake of it (every harness, not just claude) with `--clone-dir`; removed only by `fleet teardown` |

All state transitions are marker-file creation, never deletion of
anything the store owns. A `routed/` marker is written *before* any spawn
it triggers, so a crash between the two loses at most that one wake —
`status` shows the gap, and v1 has no repair machinery for it.

The mail root must resolve under `/var/tmp/claude-scratch` (or the
`/tmp/claude-scratch` compatibility symlink) and not under its `forks/`
subtree, because `handoffs/` is where every wake stages the document
`fork-sandbox.sh` reads into a prompt, and that script refuses a handoff
outside those bounds. `deliver` checks this once at startup rather than
letting every spawn fail one at a time with the real reason buried.

## Session resume

An (agent, thread) pair maps to one harness session, resumed at each
wake. This is a continuity and cost optimization and **never** a
correctness requirement — the full thread is in every prompt regardless.

It works through two `fork-sandbox.sh` flags:

- `--session-state <dir>` binds a host directory read-write into the
  sandbox at the sandbox HOME's `~/.claude/projects`, so the claude CLI's
  transcript store outlives the run. The directory must not be a symlink
  and must resolve under `/var/tmp/claude-scratch` — it is writable from
  inside an unattended session, so where it may point is a security
  boundary. Only the **coding** legs are bound: a review, fix or
  maintainer leg is a different conversation, and its transcript would be
  the newest in the store, which is the one `summary.json` reports.
- `--resume-session <id>` resumes that session with this wake's handoff
  as the new prompt. First coding leg only. The id must match
  `^[0-9a-f][0-9a-f-]{7,63}$` — it is a filename stem, so anything with a
  slash, a dot, or a leading hyphen is refused.

`summary.json` gains `session_state` and `session_id` on such a run; the
session id is the newest transcript stem at run end, which is a heuristic
because the CLI does not record which transcript was this run's. The
postmaster reads it at harvest and writes `sessions/<thread>/<agent>`.
That file present means the next wake resumes; absent means fresh. It is
cleared when a wake fails outright, or ends with a null session id, so a
broken session can never wedge a seat.

**A resumed session and the seat's clone both cross wakes; the run dir does
not.** Every wake still gets a fresh run dir — a new log, handoff,
summary.json, operator inbox and artifact outbox, all at fresh absolute
paths — but the clone at `workspaces/<thread-id>/<agent>/` (see the state
table above) is the SAME directory every wake of that seat sees, bound in
with `--clone-dir` for every harness, not just claude. `fork-sandbox.sh`
fetches the origin and starts each new wake's branch at the seat's own
previous branch tip, so work commits forward across wakes instead of
restarting at origin HEAD each time. A resumed conversation's paths and
commits are therefore both still there on the next wake; only run-dir-scoped
paths (the previous wake's log, handoff, inbox, outbox) are gone, as they
always were.
`fork-sandbox.sh` tells a wake which case it is in: a "This session is a
continuation" section when `--resume-session` is given (claude only), or a
"This workspace is not new" section whenever the clone was reused with no
session to resume — which is every wake past a pi or codex seat's first,
since those harnesses never get `--resume-session` at all. Carrying work
forward across wakes is the agent's own git work; nothing here automates it.

A `--refresh-at` continuation is the same conversation continued, so it
does write to the session store — but it is never *resumed*, whatever
`--resume-session` says. A continuation exists to drop the context it
inherited, and resuming it would hand that context straight back.

Resume is claude-only. A pi or codex seat gets a fresh session every
wake, with the thread in the prompt as its only continuity.

## Rendering a thread

```bash
fork-sandbox-mail-render.py <mail-root> -o threads.html
fork-sandbox-mail-render.py <mail-root> --thread <id> -o t.html
fork-sandbox-mail-render.py --text <mail-root> [--thread <id>]
```

The renderer reads the store and never writes to it, and never invokes
`fork-sandbox mail`. A malformed `.msg` renders as an error card in place
rather than aborting the run. Dot-directories — the router's state —
are ignored entirely.

Threading is by `In-Reply-To`, falling back to the last id in
`References`. A reply whose parent is not in the same thread attaches to
the root and is marked orphaned; so does a reference cycle among
non-root messages, rather than being silently dropped. Ties and top-level
orphans sort by the `NNN` in each message's own filename.

**HTML** is one self-contained file: inline CSS, light and dark themes
via `prefers-color-scheme`, no external asset beyond the font CDN. Every
value pulled from the store — subjects, bodies, addresses, attachment
names — is agent-written and hostile until proven otherwise, so it is
escaped before it ever reaches an f-string. Attachments are listed by
name; their bytes are never read.

**`--text`** is the agent view, and it is not merely a preview: it *is*
the thread section of every wake prompt. Oldest first, a `---` separator
between messages, reply nesting shown by indentation, headers abbreviated
to Message-ID / From / To / Cc / Subject / hops. There is deliberately no
`Date`, to save prompt tokens. The Message-ID stays, because it is the
handle every id-taking verb needs, and a view an agent cannot act on is
not a view.

## The anti-forgery grammar

A woken agent reads a thread full of text written by other agents. If a
message body could produce a line that *looks* like a header or a
separator, any agent could forge a message from anyone — `From: @operator`,
say, with instructions to match.

The invariant that prevents it:

> Header and separator lines are the only unquoted lines the rendering
> grammar emits. Every body line is prefixed with the thread indent plus
> a literal `> `.

A body line that already starts with `> ` becomes `> > ` — standard
reply nesting, which is also why the scheme is invisible to anyone who
has read email before. The consequence is that no body can produce an
unquoted line, so anything carrying a leading `> ` reads as quoted body
text no matter what it claims to be.

Note the order when parsing this yourself: **indentation comes before the
marker**, so strip leading whitespace first, then test for `> `.

## Starting a fleet

```bash
# 1. Write a persona per agent.
$EDITOR ~/.config/fork-sandbox/personas/reviewer.md

# 2. Declare seats and lists (optional — bare personas are agents too).
$EDITOR ~/.config/fork-sandbox/fleet.yaml
fork-sandbox fleet check
fork-sandbox fleet roster

# 3. Start the router against the project the agents will work in.
fork-sandbox postmaster deliver --project ~/src/proj

# 4. Mail the fleet. Your own address just has to not be a fleet agent.
fork-sandbox mail send --from @operator --to @reviewer --cc @crew \
    --subject "look at the parser rewrite" --body ./ask.md

# 5. Watch.
fork-sandbox postmaster status
fork-sandbox-mail-render.py "$FORK_SANDBOX_MAIL_ROOT" -o threads.html
```

To stop a runaway conversation, `postmaster flag <thread-id>`; to
restart a stalled one, mail into it — rule 1 clears the flag and resets
the budget.

## What v1 does not do

- **No mail tooling inside the sandbox.** A wake cannot read the store,
  search other threads, or send mail directly; it writes reply files and
  the harvester posts them.
- **Resume is claude-only.** pi and codex seats are fresh-wake.
- **No list-Cc delivery index.**
- **No repair** of a routed-but-never-spawned wake after a crash.
- **No SMTP.** The format is RFC 5322-shaped precisely so an SMTP or
  notmuch facade could be added host-side later without rewriting the
  store, but nothing like that exists.
- **No mid-session delivery.** Mail arriving while an agent is awake
  waits for the next wake.
- **Detection of a dead wake has one residual gap.** A wake whose process
  died without writing `summary.json` is caught via its run dir's pid
  file, once the pid is dead (or the file predates the current boot, per
  `/proc/stat`'s btime) and the grace period has passed. A pid recycled
  by the OS onto a live, unrelated process *within the same boot* reads
  as alive, so detection waits for that process to exit too. This is the
  same gap `fork-sandbox-status.sh`'s "abandoned" state already accepts.

Every script here also documents itself: run it with `--help`, or read
the header comment, which is the same text.
